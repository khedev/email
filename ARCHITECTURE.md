# Architecture

React renders the desktop UI and only invokes narrow, typed Tauri commands. Rust owns filesystem paths, SQLite, migrations, logging, and future transport services. The app-data directory contains `database`, `attachments`, `avatars`, `cache`, and `logs`; no user path is hard-coded.

The email (IMAP/SMTP) and messenger (future REST/WebSocket) domains remain separate. Syncable rows share UUID identity, timestamps, soft deletion, server identity, sync status, and version fields. `sync_queue` persists work before network delivery.

The email composer is local-first. It writes an outbound email, normalized recipient rows, and a `save_draft` queue item. Sending changes only the durable delivery state, files the copy into Sent and adds `send_smtp`; the `deliver_queued_mail` command then consumes that item through `transport.rs`, which opens one TLS-honoring SMTP session per account using the OS-stored credential (XOAUTH2 for Google) and either marks the message `sent` — completing the queue item, which is what makes delivery idempotent — or `failed` with a fixed, non-sensitive classification of the refusal. IMAP retrieval likewise lives behind native services, not the React UI.

The sync engine owns queue lifecycle, retry metadata, and conflict records. It accepts transport adapters through `RemoteSyncTransport`; the current adapter is explicitly disabled, so it reports offline while preserving pending work. A company REST/WebSocket adapter will share this lifecycle without sharing protocol code; the IMAP/SMTP mail transports (`mailbox.rs`, `transport.rs`) stay deliberately outside it and consume the same durable queue directly.

Mail folders are role-scoped (`inbox`, `sent`, `drafts`, `archive`, `trash`); the same role query renders every mail view and outbound rows display the first `to` recipient for their summary line. Starred mail is a flag query across folders.

Global search runs on SQLite FTS5 virtual tables kept in sync by triggers defined in migration 0007, with prefix matching for single tokens and phrase matching for multi-word queries. The UI never touches SQLite directly; `platform/tauri.ts` mirrors the native commands with strict TypeScript types.

Presence and appearance preferences are durable key/value rows in a `settings` table. The React shell applies `theme` (light/dark/system), `density`, and `font_size` through CSS tokens on the document root; the settings table is the source of truth and survives restarts.

Messenger reactions and replies are local-first. Every message belongs to a thread root (`messages.thread_id`, normalized by migration 0011; a root points at itself), and reactions are stored on that root, so a thread keeps one aggregate wherever the button was clicked. The channel history lists exactly one row per thread — pinned threads first — carrying the reply count, last-reply time and the thread's aggregate reactions, while replies load on demand in the inline thread panel. Replies are written from that panel, so a reply to a reply never opens a second thread, and deleting a root removes its replies (they would otherwise be unreachable). The browser preview backend mirrors this contract.

The accounts domain keeps credentials out of SQLite: the IMAP/SMTP password and the Google OAuth refresh token live in the OS credential manager (`Relay Mail` and `Relay Mail OAuth` services) and only a *reference* is stored on the account row. Google sign-in additionally keeps the optional OAuth client secret as its own keyring entry, while the (non-secret) client id is a `settings` row; `forget_oauth_client_id` deletes both, and a refused XOAUTH2 grant is classified as an authorization problem (`VerifyFailure::GoogleAuth`) rather than a rejected password.

Mail retrieval lives in `src-tauri/src/mailbox.rs`: it reuses `verify::open_mail_session` (so sign-in verification and fetch authenticate identically), fetches the newest inbox messages with `BODY.PEEK[]` — one whole message per response, read through `Fetch::body()`; the sectioned `BODY[HEADER]`/`BODY[TEXT]` items answer into different accessors and reading `body()` against them silently yields a header-only message (BUG-022), which is why the item is a named constant with that reasoning attached — and never marks mail read on the server. It decodes the MIME body to plain text and writes the rows through `Repositories::upsert_fetched_messages`, which is transactional and keyed by IMAP UID — a repeat sync updates in place and never re-files a message the user archived or trashed locally. `Repositories::ensure_account_folders` gives each account its five role folders, which the folder views query by role. A single message can also be fetched on demand (`fetch_message_body` by UID, via the `fetch_email_body` command), which is how a row stored before the body decoded — or one older than the newest-50 sync window — repairs itself when the user opens it; those writes go through `store_email_body`, which touches neither `sync_status` nor the queue because a body read from IMAP is remote truth rather than a local edit.

Mail delivery lives in `src-tauri/src/transport.rs`, the send half of the same transport. `Repositories::queued_sends` resolves each unfinished outbound message — `queued` (never attempted) or `failed` (retryable) with a `send_smtp` item that is not yet `completed` — into the account connection (SMTP endpoint included), the sender identity, the body and the To/Cc/Bcc lists, so the SMTP layer never touches SQLite and the completed-mark is what makes delivery idempotent. `transport::deliver` then opens one `lettre` session per account: the stored `encryption` selects implicit TLS, STARTTLS or explicitly chosen plaintext, a password account authenticates with PLAIN/LOGIN and a Google account with XOAUTH2 (the same short-lived access token the fetch path uses), and message assembly (headers, MIME encoding, Bcc kept out of the transmitted headers) is the library's. `commands::deliver_queued_mail` runs the session on a guarded worker thread — signing/credential resolution stays on the IPC thread, and the database lock is held only to snapshot the work and to write the outcomes — then records `sent` (queue item completed, error cleared) or `failed` (queue item failed, attempt counted, `last_error` set), emits a `mail-delivery-result` event per message so the open reading pane refreshes, and returns a `DeliveryReport`. Refusals become fixed, non-sensitive sentences from the response code alone (`failure_message`), never the server's text. Triggers: the shell delivers the message just queued, drains the queue once after startup, and the reading pane's **Try again** re-runs one message.
