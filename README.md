# Relay

Relay is a local-first desktop communication client built on Tauri 2, Rust, React and SQLite. It pairs a Thunderbird-style mail workspace with a company messenger (channels, replies, reactions), all powered by a local SQLite store that works fully offline.

## Run

Install Node dependencies, then `npm run dev` to browse the UI (opens in **browser preview mode** — a labeled, in-memory store replaces the native backend when no Tauri host is attached). For the real desktop app with the local SQLite backend, run `npm run tauri dev` from the project root (first run needs the Rust toolchain from `DEVELOPMENT.md` and the WebView2 runtime). `npm run build` produces the production frontend bundle; `cargo build` in `src-tauri` builds the native binary.

## What is operational now

- Responsive desktop shell with a design-token theme system (light/dark/system), density and font-size settings, keyboard shortcuts, and a Ctrl+K command palette with global search
- Mail workspace: Inbox, Starred, Sent, Drafts, Archive and Trash views backed by local SQLite; reading pane with star/archive/trash actions (drafts can be trashed), reply/reply-all/forward, mark-as-unread via the More-actions menu, and draft resume through the composer
- Composer with account selection, To/Cc/Bcc, subject, auto-saving drafts, Ctrl+Enter send; pressing Send files the outbound copy into the account's Sent folder, records a durable `send_smtp` queue item and transmits it over SMTP, then closes onto that message in Sent — whose reading pane reports the real result (queued, delivered, or the classified reason it failed, with **Try again**)
- Full offline search index (SQLite FTS5) across emails, messages, channels and contacts, kept in sync by triggers and excluding soft-deleted rows
- Messenger: channels with member counts, thread-first history (one row per thread, carrying its reply count, last-reply time, pinned state and the thread's aggregated reactions), inline thread panels where replies are written, emoji reactions with quick reactions; direct messages opened or created from Contacts with real conversation focus; message edit, delete, pin and copy actions
- Company directory: searchable contacts with favorites and add-contact flow, plus actions to email or message a person
- Email conversations: related messages grouped by `thread_id` with an expandable conversation strip in the reading pane
- Settings: appearance, presence (online/away/DND/offline), notification preferences, account add/remove (sign-in honors the selected encryption: implicit TLS, STARTTLS, or explicitly chosen plaintext; re-signing into a known address rotates its stored credential instead of failing; unreachable servers fail fast with a clear reason; server refusals are classified into actionable hints — Gmail/Google Workspace, Yahoo and iCloud require an **App Password**, normal passwords are refused by those providers for IMAP), storage usage + cache clearing, and sync status/retry
- Google sign-in for Gmail (OAuth 2.0 / XOAUTH2): the native layer runs the full installed-app flow — PKCE S256, an ephemeral loopback redirect listener, the system browser, token exchange over TLS — then verifies IMAP access with XOAUTH2 before storing anything; the refresh token lives in the OS credential manager. Requires your own Google Cloud OAuth client id (type *Web application*, authorized redirect URI `http://127.0.0.1`), which is remembered after the first successful sign-in
- Mail retrieval (IMAP): the Mail view's **Sync** action fetches the newest inbox messages from the server into the local store (`BODY.PEEK[]` — the whole message, so the body decodes, and `PEEK` so fetching never marks mail read on the server), decodes MIME/base64/quoted-printable and RFC 2047 subjects, reduces HTML messages to text, and stores them keyed by IMAP UID — so a repeat sync updates in place and never resurrects mail you archived or trashed. One fetch runs automatically after the first sign-in, and opening a message whose stored body is empty downloads just that message
- Mail delivery (SMTP): the durable `send_smtp` queue is consumed by `src-tauri/src/transport.rs` — one session per account honoring the stored encryption (implicit TLS / STARTTLS / explicitly chosen plaintext), AUTH PLAIN/LOGIN, or XOAUTH2 for Google accounts through the same short-lived access token the fetch path uses. Delivery runs when a send is queued, once on startup to drain anything a quit left behind, and on demand from the reading pane's **Try again**; a message is marked `sent` (and its queue item completed, which is what stops it being sent twice) or `failed` with a fixed, non-sensitive classification of the refusal. Message assembly (headers, MIME, Bcc kept out of the transmitted headers) is `lettre`'s; success and refusal both take the store's ordinary path (attachments, other folders and background/scheduled sync remain later phases)
- Thunderbird-style auto sign-in: enter only an email address and password — the native layer discovers the IMAP/SMTP configuration from its built-in provider database, DNS MX records (Google Workspace / Microsoft 365 detection), Mozilla + domain autoconfig XML, and hostname guesses, verifies the password against each candidate (SSL 993 before STARTTLS 143, plaintext never auto-tried), and streams live progress to the login screen; manual setup and Google sign-in remain available as fallbacks
- Notification history and preferences, native notification command, sync queue with durable lifecycle, retry and conflict tables, repository-backed CRUD
- Browser preview backend (`src/platform/preview.ts`): a type-compatible in-memory store so `npm run dev` is fully explorable outside Tauri, with a `Preview` badge and console diagnostics when the native backend is unavailable
- Tests: Vitest frontend unit tests (`npm test`; `src/app/util.test.ts` plus the preview-backend thread and send contracts in `src/platform/preview.test.ts`) and a Rust test suite of 52 integration tests (migration/database incl. the thread backfill on legacy data, repositories, FTS5 search, threading, threaded-reply normalization and thread-delete cascade, reactions, sign-in refusal classification against real provider answers and protocol-shaped failures, settings/presence, conversations/DMs, message edit/delete/pin, sync queue, verified sign-in, queued-send folder filing and delivery snapshot/sent/failed/retry transitions, SMTP refusal classification, outbound message assembly incl. Bcc handling, a loopback SMTP delivery over a real socket, self-identity recovery, Thunderbird-style discovery, IMAP fetch-window and message-body assembly/repair, resolver-runtime and command-panic regressions) — see `DEVELOPMENT.md`

IMAP retrieval and SMTP delivery are implemented (the Mail view's Sync action and the send/deliver path); OS credential storage for company sync and company-server sync are intentionally not claimed; they belong to later phases and will consume the existing durable queue.
