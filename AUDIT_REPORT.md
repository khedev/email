# AUDIT_REPORT — Relay Desktop

Audit date: 2026-09-15 · Scope: full application (frontend, Tauri IPC, Rust, SQLite, docs)
Method: static read of every source file, IPC cross-reference, build + test runs (`npm run build`, `npm test`, `cargo test`, `cargo clippy`), targeted regression tests for every fix.

## Executive Summary

Relay is a genuinely local-first application: all data lives in SQLite (WAL, FK enforced), every UI mutation goes through typed Tauri commands into a single repository layer, secrets live in the OS credential manager, and the sync/transport gaps are honestly labeled. The audit found **no deceptive fake functionality**; the browser "Preview" backend and the debug seed data are legitimate, labeled development tools.

What was broken fell into four groups: (1) durable write paths that did not update the views users look at (queued sends never reached the Sent folder), (2) a UI↔backend wiring gap (the `open_direct_message` command existed but was never called, so "Message contact" did nothing), (3) a release-only identity bug (messenger writes referenced a contact row that only the debug seed created), and (4) assorted dead buttons and silent-failure UX. All of these are fixed and regression-tested.

## Problems Found and Fixed

### High (core functionality broken)
1. **Queued sends never appeared in Sent** — `queue_send` only set `delivery_state='queued'`; the email stayed in Drafts, so the Sent view could only ever show the seed row. *Fixed:* queue_send now files the outbound copy into the account's Sent folder and rejects nonexistent ids. (test: `queued_send_moves_mail_into_the_sent_folder`)
2. **"Message contact" did nothing useful** — the `open_direct_message` IPC command existed but the UI never called it; it passed a *contact id* where a *conversation id* was expected. *Fixed:* the UI calls the command, opens/creates the DM, and focuses the returned conversation; failures show a visible error in the workspace.
3. **Messenger identity existed only in debug builds** — reactions and channel membership carry foreign keys into `contacts`, but the self row (`dev-self`) was created only by the debug seed, so release builds failed those writes; `send_message` also returned a hard-coded `"Alex Morgan"` name. *Fixed:* `ensure_self_identity()` runs on every `Database::open` (all builds), is kept in step with the signed-in account, and sent messages are read back from the row. (test: `local_user_identity_survives_without_the_development_seed`)
4. **Channels were listed as direct messages** — `conversations()` returns both kinds (contract asserted by tests), and the sidebar rendered everything under "DIRECT MESSAGES". *Fixed:* the DM section filters `kind === 'dm'`.

### Medium
5. **Search returned soft-deleted messages/conversations** — FTS joins had no `deleted_at IS NULL` filter. *Fixed on all four queries.* (test: `search_ignores_soft_deleted_messages`)
6. **Trash always failed on drafts** — folder moves required `direction='inbound'`. *Fixed:* outbound mail is movable. (test: `trash_accepts_outbound_mail`)
7. **Opening a folder silently marked the newest email read** — auto-selection triggered the auto-read path. *Fixed:* only deep-linked selections (search/jump) open an email; browsing never mutates read state.
8. **Replying in a thread did not bump the reply count** — *fixed* with an optimistic update.
9. **Dead buttons** — "More actions" is now a working menu with **Mark as unread** (backend capability that previously had no UI); "Help & feedback" opens an honest about + shortcuts panel; the profile avatar shows the signed-in account's real initials and opens Settings.
10. **Sidebar "Threads"/"Channels" placeholders** — both features exist inside Messages; the items now navigate there instead of a stub screen.

### Email login follow-up repairs
11. **The UI discarded the backend's specific sign-in errors** — Tauri rejects failed commands with a plain string, and `err instanceof Error` is always false, so every failure showed a generic line. *Fixed* with a `commandError` helper used by the login screen and the Settings sign-in/connection-test handlers; the classified messages ("server rejected these credentials", "unable to reach the mail server (…)") now reach the user.
12. **Re-signing into an existing address destroyed its stored credential** — the keyring entry was overwritten, then deleted when the UNIQUE email index rejected the second INSERT, leaving the original account unable to load its password. *Fixed:* sign-in is idempotent (`account_by_email` → rotate secret → refresh connection state on the existing row). (test: `re_sign_in_updates_the_existing_account`)
13. **Unreachable mail servers hung the sign-in spinner for the OS TCP timeout (~20s+)** — *fixed* with a bounded 5-second reachability probe before the IMAP handshake, so dead hosts/DNS failures fail fast with the right recovery hint.
14. **The post-sign-in empty Inbox misread as "login did nothing"** — its copy now states honestly that mail retrieval (IMAP sync) is a planned phase and nothing is fetched into the local store yet; the header identity also refreshes immediately after the first sign-in.
15. **Gmail/App-Password rejection was opaque** — the server's refusal code (e.g. `AUTHENTICATIONFAILED`) was discarded, so users testing Gmail/Workspace with their normal password got no guidance. Refusals are now classified into fixed, non-sensitive hints (credentials refused / rate-limited / unavailable / mechanism refused) with provider-specific App-Password instructions, the login screen shows per-provider hints, and servers that disable inline LOGIN are retried with AUTHENTICATE PLAIN. Raw server text is never echoed (password-safety). (test: `sasl_plain_encoding_and_refusal_classification`)
16. **Gmail now also supports Google sign-in (OAuth 2.0 / XOAUTH2)** — the previously "future phase" OAuth flow is implemented natively (`src-tauri/src/oauth.rs`): PKCE S256 + `state`-validated loopback redirect (RFC 8252), token exchange via `ureq`/native-tls, id_token address extraction, an IMAP XOAUTH2 proof before anything is stored, refresh-token storage in the OS keyring (`Relay Mail OAuth` service, JSON with the client id), idempotent re-authorization, an OAuth-aware `test_email_connection`, and OAuth cleanup on account removal. The login screen documents the one requirement Google imposes: the user's own OAuth client id (Web application type, redirect URI `http://127.0.0.1`). Live end-to-end verification requires that client id plus a real Google account — reported as not yet live-tested. (test: `google_oauth_helpers_match_specifications`)
17. **Thunderbird-style auto sign-in** — the login screen now leads with the Thunderbird flow: just an email address and password. A new `discover.rs` collects IMAP candidates from the built-in provider database (Gmail, Outlook/365, Yahoo, iCloud, Fastmail, Zoho, GMX, Web.de, Yandex, AOL), DNS MX records via `hickory-resolver` (detects Google Workspace and Microsoft 365 custom domains), Thunderbird-compatible autoconfig XML (Mozilla DB + the domain's own well-known locations, parsed without a new XML dependency), and hostname guesses — then authenticates against each candidate (SSL 993 before STARTTLS 143, plaintext never auto-tried, de-duplicated, capped at 8) with live progress streamed to the UI. A credentials refusal stops the run immediately with the classified guidance; only unreachable candidates are skipped. The OAuth client id is persisted in the settings table after the first Google sign-in so it is only ever entered once. Manual setup remains available as a fallback. Live DNS/autoconfig fetches are not separately live-verified; all offline-computable logic is specification-tested. (test: `thunderbird_style_discovery_ranks_and_parses`)

18. **Auto sign-in crashed the whole app on a custom-domain address** — the MX lookup built its Tokio runtime with `enable_io()` only, but hickory wraps every name-server connection in `TokioTime::timeout`, so the first DNS query panicked ("A Tokio 1.x context was found, but timers are disabled"). Because commands are invoked from the WebView2 IPC callback on the UI thread, that panic hit a frame that cannot unwind and aborted the process (`STATUS_STACK_BUFFER_OVERRUN`, exit `0xC0000409`) instead of showing an error. *Fixed:* `discover::resolver_runtime()` enables the timer driver (test: `mx_lookup_runtime_keeps_timers_enabled`), and the network-touching commands plus the discovery thread run under `guard::guarded`, which converts a panic into the normal failed-command result (test: `panics_in_command_work_become_errors`). Discovery also moved off the UI thread onto a worker thread awaiting a `tokio::sync::oneshot`, so the window no longer freezes for the seconds the DNS + IMAP probing takes.

19. **Google sign-in could not use a client secret, and stored Google credentials could not be removed** — the OAuth pane accepted only a client id, so a *Web application* client (which Google requires to present its secret on the token exchange) could never complete a sign-in, the secret had nowhere to live, and a remembered client id could not be cleared from the UI at all. *Fixed:* the pane takes an optional client secret — a *Desktop app* client still works without one — and lists Google's required steps (client type, redirect URI, Gmail API, the unverified-app warning). The secret is stored in the OS credential manager as its own `Relay Mail OAuth` entry (never in the settings table, which every settings command can read) and is joined to both the code exchange and later refreshes. A new `forget_oauth_client_id` command deletes the remembered client id row and that keyring entry together (backed by `Repositories::delete_setting`, idempotent and key-validated), and the pane shows *Forget the saved Google client (id and secret)*. Both halves of the client are validated in the UI and again in the native layer before a browser round-trip, and a pasted value is never echoed back. Google's structured token errors now map to fixed hints (bad id, bad secret, redirect mismatch, cancelled, revoked, scope, Gmail API not enabled) instead of one generic line. (tests: `google_oauth_client_validation_and_error_hints`, `oauthClientSecretIssue`, the preview OAuth parity tests)
20. **A refused Google authorization was reported as a rejected password** — `verify_xoauth2` reused the password classifier, so a revoked or expired grant produced "the mail server rejected this sign-in (the credentials were refused)…" together with App-Password instructions that cannot help, and Gmail's older wordings ("Username and Password not accepted", "Less secure app access is off") fell through to "no specific reason". *Fixed:* XOAUTH2 refusals are now classified on their own (`VerifyFailure::GoogleAuth` + `xoauth2_refusal_hint`), keeping the shared protocol/configuration split, and are answered with "start the Google sign-in again / remove Relay at myaccount.google.com/permissions" — a refused authorization never suggests an App Password. The password classifier gained the two Gmail wordings. (test: `gmail_refusal_diagnostics_cover_password_and_oauth_paths`)

21. **Gmail sign-in could not succeed through the app's primary button** — the discovery flow identified `imap.gmail.com` correctly, then always attempted a **password** IMAP LOGIN, which Google refuses by policy for consumer mailboxes. The refusal was classified as an ordinary bad password ("the credentials were refused") and the run aborted, so the user was told to check a password that could never work. *Fixed:* the discovered configuration now carries its authentication method (`MailCandidate.auth_method`), consumer Google mailboxes are flagged `"oauth2"`, and a refusal on Google's own IMAP host is reported for what it is — "Google does not accept account passwords for IMAP — sign in with Google, or create an App Password" (`refusal_hint_for`). The login screen leads with **Continue with Google** for a Gmail address and keeps "Use an App Password instead" available. (test: `gmail_password_refusal_is_routed_to_google_sign_in`)
22. **The Google sign-in froze the window for up to 5 minutes, and a cancelled sign-in reported a timeout** — `google_oauth_sign_in` was synchronous, so the loopback wait (`AUTH_TIMEOUT` = 300 s) ran inline on the WebView2 IPC thread; and `wait_for_code` returned only on a valid code, so Google's consent-denial redirect (`?error=access_denied`, no code) was treated as "nothing arrived yet" and waited out the deadline. *Fixed:* the command is now `async` and runs the browser half on a `relay-oauth` worker thread; the loopback callback is classified into grant / refusal / unknown, so a refusal returns immediately with "Google sign-in was cancelled…"; and an explicit **Cancel** action (`cancel_google_sign_in` + an app-level flag) returns at once. (test: `oauth_loopback_separates_grants_from_refusals`)
23. **Sign-in blocked the whole app (BUG-004 / SEC-003) and a cleartext autoconfig fallback could leak the password (SEC-001)** — `test_email_connection` held the single global database mutex across HTTPS + IMAP; and discovery fetched `http://autoconfig.<domain>/…`, which a network attacker could answer with their own IMAP host and then receive the mailbox password. *Fixed:* the check now snapshots under the lock, releases it for the network phase and re-locks only to record; discovery uses HTTPS sources only. The sign-in state also became an explicit `AuthState` (with a visible warning instead of a silent fail-open) and follows account changes immediately, so removing an account no longer leaves a stale "signed in" shell (BUG-016).

24. **Signed in, but no mail ever appeared — and the folder scaffolding was missing** — two defects stacked. (a) There was **no IMAP fetch worker at all**: sign-in only *verified* access, so the local store stayed empty. (b) Worse, `emails_in_folder` filters on a folder *role*, and `add_account_verified` never created folder rows — only the debug seed and `move_email_to_folder` did — so a real account had none and its inbox was empty by construction even with mail stored. *Fixed:* a new `src-tauri/src/mailbox.rs` fetches the newest 50 inbox messages over the authenticated session (`UID FETCH` with `ENVELOPE`, `FLAGS`, `INTERNALDATE` and `BODY.PEEK` so fetching never marks mail read), decodes MIME/base64/quoted-printable/RFC 2047 and reduces HTML to text (never rendering it), and stores them in one transaction keyed by IMAP UID; `Repositories::ensure_account_folders` creates the five role folders on sign-in and again before each sync (repairing existing accounts). The Mail view gained a **Sync** action with live progress, one automatic fetch after the first sign-in, and an inbox empty-state that says whether a sync has run. A sync refreshes content but never re-files a message the user archived or trashed locally. (tests: `mailbox_decodes_real_message_shapes`, `accounts_own_their_folders_and_fetched_mail_becomes_visible`)

25. **A sync reported "downloading" and then "no new mail" while downloading nothing** — the FETCH range was built from `inbox.exists` (a count in IMAP **sequence** space, RFC 3501 §6.4.6) and then handed to `uid_fetch`, which reads its range as **UIDs** (§6.4.8). On any mailbox whose UID numbering has advanced past its current size — every mailbox that has ever had a message deleted — that matches nothing, the FETCH returns an empty response, and the run completes with a zero count that is indistinguishable from an empty mailbox. *Fixed:* the range now goes to the sequence-based `Client::fetch`, it is produced by an extracted `newest_sequence_range(exists, cap)` named for the ID space it uses, and a short FETCH now logs the requested/received counts so this class of failure is observable. *Also fixed in the same pass:* `sync_mail` took a single account id that the UI picked as `accounts[0]`, while the account list is ordered by display name — so the seeded demo account (or any alphabetically earlier one) could be synced instead of the mailbox on screen; it now takes optional ids and **defaults to every signed-in account**, reporting per-account failures instead of hiding them behind a zero count. The automatic first sync moved from `App` (console-only) into the Mail view, where a failure renders in the note the user is looking at. (tests: `newest_sequence_range_covers_the_tail_of_the_mailbox`, `sync_targets_every_signed_in_account`)

26. **Every message was stored with an empty body, so an opened email showed only its subject** — `fetch_inbox` asked the server for `BODY.PEEK[HEADER]` and `BODY.PEEK[TEXT]`, then reassembled the message from `fetch.header()` and `fetch.body()`. In the pinned `imap` crate `Fetch::body()` matches only the **unsectioned** `BODY[]` item (`section: None`); a sectioned response is keyed `Some(Full(Header))`/`Some(Full(Text))` and read through `header()`/`text()`. Since `BODY[]` was never requested, `body()` returned `None` for every message, the assembled message was the header block plus one blank line, and `text_body_of` decoded it to `""`. Retrieval looked successful — the row was written, and the subject/sender/date (from `ENVELOPE`) rendered — so the symptom presented as a broken reading pane rather than a broken fetch, and no existing fixture could catch it because the bug was in *which response field is read*, one layer above the well-tested MIME decoding. *Fixed:* the fetch now asks for one complete message (`FETCH_FULL_MESSAGE = "BODY.PEEK[]"`, still `PEEK` so nothing is marked read), and `assemble_raw_message(full, header, text)` rebuilds the message from whichever sections arrive so either response shape decodes. Because a sync only revisits the newest 50, rows already stored empty needed their own path: `mailbox::fetch_message_body` downloads one message by UID, the new `fetch_email_body` command writes it back through `Repositories::store_email_body` (which deliberately does not touch `sync_status` or enqueue — a body read from IMAP is remote truth, not a local edit), and the reading pane calls it when an inbound message opens with an empty body, showing the text it downloads, a "this message has no readable content" state when there genuinely is none, and a count-only log line when a fetch yields unreadable bodies. (tests: `raw_message_assembly_keeps_the_body`, `stored_email_body_can_be_repaired`)

27. **“Send” looked broken because the UI hid what it had actually done** — the send path was correct (the outbound copy is filed into Sent, `delivery_state = 'queued'`, one pending `send_smtp` item) but nothing on screen said so. The success text was a developer note (*“Queued for SMTP delivery when a transport is configured. Keep it local for now.”*); the composer stayed open over the unchanged Inbox, so a success was indistinguishable from a no-op; pressing Send with no account selected did nothing and said nothing (`persist()` returns `undefined`, and `send()` returned before setting any status); every backend failure was reported as a bad recipient, because the handler collapsed all four `AppError` variants with `map_err(|_| …)` — a storage failure during the Sent filing produced a false instruction about recipients; and the reading pane rendered a queued message exactly like delivered mail even though `delivery_state` already reached the UI. *Fixed:* the composer hands the queued id to the shell, which closes it and opens that message in Sent, so the visible result of Send is the message itself; the reading pane states “Not delivered yet. This message is saved in Sent on this computer. This build has no mail transport, so no copy has left the machine.”; an empty account selection is reported instead of silently ignored; `queue_email_send` matches `AppError` exhaustively so only a genuine validation failure carries the recipient hint; the composer's save failure surfaces the backend's own wording through `commandError`; and the preview backend mirrors the contract (recipient validation + the move into Sent) so `npm run dev` no longer loses a queued send. (tests: `queued_send_records_one_pending_delivery_item`, `queue_send_requires_a_to_recipient`, preview `preview local-only send`)

28. **A Cc/Bcc-only draft made the Drafts view unopenable** — `list_emails` titled an outbound row with a scalar subquery over `email_recipients` filtered to `recipient_type = 'to'`, read into a non-nullable `String`. A draft with no To recipient (Cc/Bcc only, or one still being typed — which is the state autosave persists after 700 ms) made that subquery return SQL `NULL`, so `row.get(1)?` failed with `InvalidColumnType(…, Null)` and the **whole listing** aborted: `emails_in_folder("drafts")` returned `Err(Database(…))`, the command answered “Unable to load local folder”, and the view rendered its error state with no rows and no empty state. The draft was then unreachable from the UI — it could not be selected, resumed or trashed to recover. *Fixed:* the title expression wraps the subquery in `COALESCE` and falls back through `cc`/`bcc` before reusing inbound mail's sender chain (`sender_name` → `sender_email` → account display name → `'Unknown sender'`), with the two SQL fragments named (`addressed_to`, `sender_fallback`) so the intent is readable. (test: `draft_without_a_to_recipient_still_lists`)

### Low / cleanup
11. `tsc -b` no longer litters `vite.config.js`/`.d.ts`/tsbuildinfo into the repo root (emits to `node_modules/.cache/tsc-node`); stale artifacts deleted.
12. `verify.rs` previously relied on the crate's implicit port rule; it now explicitly honors the configured encryption (`ssl` = implicit TLS, `tls` = STARTTLS, `none` = plaintext, unknown = auto).

## Unused Code (reported, intentionally kept unless noted)

- IPC commands never called by the UI: `get_database_info`, `get_pending_sync_items`, `show_native_notification`, `get_inbox`. Kept as a deliberate native API surface; `getInbox` remains exported in `platform/tauri.ts`.
- `email_attachments` table + attachment UI placeholder: the composer attach button is disabled with an honest tooltip; no writer exists yet.
- `tauri-plugin-opener` is registered but never invoked; `pnpm-lock.yaml` coexists with `package-lock.json` (npm is the toolchain of record). Removal is safe but left to the maintainer.

## Security Findings

- No plaintext secrets anywhere: passwords go to the OS credential manager; SQLite stores only `credential_ref`; verified by test (`verified_sign_in_persists_state_and_keeps_secret_out_of_the_database`, `os_keyring_round_trip`).
- SQL is parameterized; the only string-interpolated SQL uses a whitelisted role.
- Email HTML is never rendered (text only, React-escaped); CSP and Tauri capabilities are narrow; no `.env`/secrets in the repo; failures are logged under `[relay]` without secrets.
- Plaintext IMAP (`none`) is available but explicitly labeled "not recommended" in the UI.
