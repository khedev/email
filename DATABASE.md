# Database

The first migration establishes accounts, email folders, contacts, conversations, messages, and a durable sync queue. The second migration adds the cached email store used by the local inbox. SQLite WAL and foreign keys are enabled at connection setup.

`repositories.rs` is the only CRUD layer. UI code accesses it through typed Tauri commands, never SQLite directly. Debug builds seed a small isolated dataset only when a fresh database has no accounts (mail folders for every role, drafts, queued outbound mail, channels, threaded replies, contacts with directory metadata, notifications); release builds start empty. Mutations also create durable sync-queue work for a later transport service.

Phase 3 adds normalized `email_recipients` and `email_attachments`, plus outbound delivery state on cached emails. Drafts and send requests are persisted before any SMTP work is attempted. The `send_smtp` queue operation has no active transport worker yet: it is intentionally durable but pending. Queueing a send files the outbound copy into the account's Sent folder, so the Sent view always reflects queued work. Folder-scoped queries (`emails_in_folder`) render Inbox, Sent, Drafts, Archive and Trash from role columns; moved mail updates `folder_id` and re-enqueues (outbound mail moves too, so drafts can be trashed).

Phase 4 adds channel membership, message reactions, and reply threads. Company messages remain in `conversations` and `messages`, isolated from the email tables. New messages and reactions are stored locally first and create durable queue work for the future company API/WebSocket transport. The local user's messenger identity is a real contact row (`repositories::SELF_CONTACT_ID`): it is created at startup in every build (`ensure_self_identity`, not only the debug seed), kept in step with the signed-in account, and anchors the "mine" flag, reactions, and channel-membership foreign keys — so messenger writes work in release builds with no seed data.

Phase 5 gives `sync_queue` a durable lifecycle (`pending`, `syncing`, `completed`, `failed`) and lock/completion timestamps. `sync_conflicts` preserves both local and remote versions until a user or policy resolves them; it never overwrites a local change silently. `sync_metadata` records synchronization checkpoints.

Phase 6 adds durable notifications with read state and optional entity links, plus individual notification preferences. The UI reads these records from native commands; native OS delivery is an additional presentation channel, not the source of truth.

Migration 0007 adds a key/value `settings` table (appearance + presence) and FTS5 search virtual tables for emails, messages, contacts and conversations, kept in sync with triggers and backfilled for databases created by earlier migrations.

Migration 0008 recreates those FTS indexes as **external-content** tables (`content='…'`, `content_rowid='rowid'`). Integration tests proved the original contentless design unsalvageable: its `'delete'` trigger form is invalid without old column values (breaking every UPDATE/DELETE on indexed tables - stars, read state, reactions), and contentless tables cannot return column values (breaking all search reads). External-content indexes restore trigger-based writes, resolve display columns through the content table, and support the canonical `VALUES('rebuild')` backfill; search queries join the base tables on the indexed `id` column.

Migration 0010 adds account sign-in state (`connection_state`, `connection_error`, `credential_ref`, `last_verified_at`). Sign-in verifies the password against the real IMAP server first (`verify.rs`); only then is the account persisted with a `connected` state, while the password itself goes to the OS credential manager (`security.rs`) — never into this database (see SECURITY.md).

Migration 0011 normalizes messenger threading. Replies used to be reachable only through `messages.reply_to_id`, so a reply to a reply silently started a second thread and a reaction landed on whichever bubble was clicked. `messages.thread_id` now stores the id of the thread's root (a root points at itself) for every message, and `messages.in_reply_to` keeps the exact message that was answered; `reply_to_id` stays as the parent pointer the sync payload needs. The backfill walks each row up the reply chain with a recursive CTE, so pre-0011 replies — including replies to replies — collapse onto their original root. The repository layer enforces the model: `send_message` rejects replies whose target is unknown or belongs to another conversation and derives `thread_id` from the resolved parent; `channel_messages` returns exactly one row per thread (pinned first, then chronological) carrying `reply_count`, `last_reply_at` and the thread's aggregated reactions; `message_thread` resolves any thread member to that thread's replies; `toggle_message_reaction` always stores the reaction on the root; and `delete_message` cascades a deleted root to its replies, which would otherwise become unreachable because the history only lists roots.
