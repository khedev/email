# Development

Use `npm run build` to type-check and build the frontend, and `npm test` to run the Vitest unit tests. Use `cargo check`, `cargo test`, and `cargo build` in `src-tauri`. Do not treat development seed data as production data; repositories and services must remain native-side.

## Toolchain (Windows, this machine)

Rust was installed with `winget install Rustlang.Rustup`. The **GNU-hosted** stable toolchain (`stable-x86_64-pc-windows-gnu`) is the default, because this machine has no Visual Studio / MSVC and the MSVC host requires Visual Studio's import libraries (`kernel32.lib`, ...) even with rust-lld. The C compiler required by rusqlite's bundled SQLite comes from **MSYS2** (extracted to `C:\Users\bualk\msys64`; `pacman -S mingw-w64-x86_64-gcc`). Both must be on `PATH`:

```
C:\Users\bualk\.cargo\bin
C:\Users\bualk\msys64\mingw64\bin
```

`src-tauri/.cargo/config.toml` points the toolchains at `rust-lld` (shipped with rustc). It avoids GNU `ld` (which fails on the large symbol count, "export ordinal too large" / PE 65,535 export limit) and Visual Studio's `link.exe` (not installed).

**Test-binary manifest:** the unit-test binary links the same comctl32 v6-only imports as the app binary but receives no application manifest, so the Windows loader binds comctl32 v5 and refuses to start it (`STATUS_ENTRYPOINT_NOT_FOUND` before `main`). `src-tauri/build.rs` therefore compiles `windows/test-manifest.xml` (Common-Controls v6 dependency) with `windres` and injects it into test targets via `cargo:rustc-link-arg-tests`. Because the lib's own unittest harness is never patched, unit tests live in the real integration target `src-tauri/tests/local_store.rs` and `[lib] test = false` disables the harness build. Plain `cargo test` just works.

`src-tauri/icons/icon.ico` is generated by `scripts/gen-icon.c` (a small standalone C program; recompile with `gcc gen-icon.c -O2 -o gen-icon.exe`). It is required by tauri-build to embed the Windows resource.

## Running the app

Two distinct ways to run the frontend, and they are different code paths:

- **`npm run dev`** - opens in a **browser preview mode**. There is no Tauri host, so `platform/tauri.ts` routes every command to `platform/preview.ts`, an in-memory store that mirrors the native command contract (same types/shapes). Data is not persisted, and a `Preview` badge is shown in the top bar.
- **`npm run tauri dev`** (from the project root; runs `npx tauri dev`) - the real desktop app. Vite serves the frontend (`beforeDevCommand`) while Rust builds and launches the window with the full SQLite/IPC backend. Requires the Rust toolchain above and the WebView2 runtime on Windows.

When a command fails natively, the UI keeps its friendly message but logs the underlying reason to the console under a `[relay]` prefix - never silent failures.

Commands are invoked from the WebView2 IPC callback on the UI thread, so blocking work must not run there. `auto_sign_in` hands discovery (DNS plus one IMAP handshake per candidate) to a plain OS thread and awaits a `tokio::sync::oneshot` - deliberately not `tauri::async_runtime::spawn_blocking`, whose pool threads already sit inside the async runtime context and would make the resolver's own `Runtime::block_on` fail with "Cannot start a runtime from within a runtime". `google_oauth_sign_in` follows the same pattern: its browser half waits for a *human* (up to `oauth::AUTH_TIMEOUT`), so it runs on a `relay-oauth` worker thread and awaits a `oneshot` while the UI stays live — the app-level cancel flag returns it early. `sync_mail` runs its IMAP download on a `relay-mail-sync` worker thread for the same reason, reading the credential on the main thread first so the worker touches no application state. `test_email_connection` is synchronous but takes the database lock only to snapshot the account and to record the result, never across the network calls (BUG-004 / SEC-003). The synchronous commands that touch the network (`add_email_account`, `test_email_connection`) and both worker threads are wrapped in `guard::guarded`: a panic escaping into that IPC frame cannot unwind and kills the process (`STATUS_STACK_BUFFER_OVERRUN`) instead of failing the action, so the guard converts it into an ordinary command error and logs it. A panic raised while the app-state mutex is held poisons it, after which commands report "Application state is unavailable" - the deliberate trade-off of not aborting.

## Building the desktop app

`tauri build` means "compile **and bundle**"; there is no per-artifact target like `exe`, and **any extra word after `build` is forwarded to cargo** — which is why `tauri build exe` fails with `error: unexpected argument 'exe' found` from `cargo build`. Use the three scripts instead:

- **`npm run build:app`** — `tauri build --no-bundle`: type-checks and builds the frontend, then compiles the release binary only. Produces `src-tauri/target/release/relay.exe` (about 31 MB; ~8 minutes on a cold cache, under a minute once the dependency graph is warm).
- **`npm run build:installer`** — `tauri build --bundles msi`: the same binary plus an MSI under `src-tauri/target/release/bundle/msi/`.
- **`npm run build:installer:nsis`** — `tauri build --bundles nsis`: the NSIS setup `.exe` (in `bundle/nsis/`). **Needs network on first use**: Tauri downloads NSIS from GitHub once, and with no DNS the step fails as `io: No such host is known. (os error 11001)`. WiX (for the MSI) is cached the same way, under `%LOCALAPPDATA%\tauri\WixTools314`, so MSI builds work offline afterwards.

All three run `build.beforeBuildCommand` (`npm run build`) first, so `dist/` is always current.

`bundle.icon` in `tauri.conf.json` must list `icons/icon.ico` explicitly. The app binary embeds the icon through the build script, but the **bundler** only looks at what `bundle.icon` declares — without it, every bundling attempt fails with `Couldn't find a .ico icon` even though the file exists (`src-tauri/icons/icon.ico`, generated by `scripts/gen-icon.c`). A standalone `relay.exe` needs the WebView2 runtime on the target machine (preinstalled on Windows 11 and current Windows 10); an installer handles the missing case.
